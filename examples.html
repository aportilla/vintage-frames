Vintage Frames

Lit web components that emulate classic Mac OS System 7 — racing-stripe title bars, 1px black borders, hard offset shadows, Chicago-style bold type. Every demo on this page is a live component.

Install

npm install vintage-frames
import 'vintage-frames'             // registers every <vf-*> element
import 'vintage-frames/vintage.css' // OPTIONAL page defaults (desktop bg, body face)

The second import is genuinely optional. Every visual constant is a --vf-* custom property with an inlined fallback, and the two System 7 bitmap faces register themselves on document.fonts from inside the components — so a component dropped on a blank page renders correctly with no global CSS at all. vintage.css only adds page-level defaults (gray desktop background, the body face on <body>), which are right for a faux desktop and wrong for a documentation page like this one. This page does not load it.

Individual components can be imported from their own modules (vintage-frames/dist/components/vf-button.js) when you want finer-grained loading; the package root registers all of them.

Sizing takes care of itself

Components are authored in system pixels — the 1-bit art grid — and each one maps a system pixel onto a whole number of device pixels by itself, so the artwork stays crisp at any devicePixelRatio and re-adapts when the window moves to a different display. It is internal, it needs no setup, and nesting never compounds it.

What follows from that: a component's box is never stated in fixed CSS pixels. Windows and dialogs declare their own size in system px — <vf-window width="240" height="176"> — and for anything else a demo below sizes in em against the component's own type (on a vf-* host 1em is the kit's 16-pixel face, so 15em is the same box on every display) or as a percentage of its container. Page furniture around the components stays in ordinary px, as your own layout would.

One thing a host page decides

Everything else in this reference is per-component. This one is page-wide, and getting it wrong is what makes an otherwise correct integration look muddy — so it comes first: the device-pixel grid.

Staying on the device-pixel grid

A component is built entirely from whole system pixels, so every edge inside it sits on the grid — but only relative to its own origin. Land that origin, or its size, on a fractional device pixel and the whole 1-bit interior rasterizes wrong: pixel-stepped corners staircase asymmetrically, hairline borders and bitmap glyph stems smear across two device rows and go gray. Mapping a system pixel onto a whole number of device pixels is the kit's own half of that and it is handled internally. Two rules are the page's, and one call covers the first:

  1. State every line-height in whole pixels, and keep padding, margin and gap on integers — or call applyGridSnap() and forget it. Line boxes are the biggest offender: 1.65 × 17px = 28.05px, and every line of prose nudges everything after it further off.
  2. Position a box that contains components from its start edge — or give it a whole-pixel size. Anything right-aligned, centered or sharing space-between computes its origin as edge − width, so a width derived from a text run lands it off the grid. 
import { applyGridSnap, requestGridSnap } from 'vintage-frames'

applyGridSnap()    // every component measures its own paint and cancels the
                   // fractional remainder — returns a cleanup function
requestGridSnap()  // re-run after moving components in a way that resizes nothing

The correction is applied inside each component's shadow root, so the host's own position, left/top and margin are never touched and it cannot collide with your layout. Its whole footprint on your DOM is two reserved custom properties (--vf-snap-dx / --vf-snap-dy) on each corrected host. Opt a single element out with the nosnap attribute.

This page calls it. Load ?nosnap to turn it off and A/B at 100% zoom. Text you set on the kit's own faces has another option: vf-paragraph and vf-label state their line box in whole system pixels themselves.

npm run verify:grid checks every vf-* host on a page at dpr 1/2/3, and npm run verify:snap checks that a page knocked off the grid gets back on it. Point them at your own pages with VF_GRID_PAGES / VF_SNAP_PAGES.

Standards & conventions

The rest of this page documents what the kit adds. Everything a control shares with the platform behaves the way the platform says it does, and is stated once here rather than repeated per component.

Attributes and properties

Every documented property is also an attribute of the same name in lowercase (cellWidth → cell-width is the only camelCase pair). Boolean properties are boolean attributes: present means true, and the value is ignored — disabled and disabled="false" both disable. Set a boolean to false from JavaScript (el.disabled = false) or remove the attribute.

Form participation

The value-bearing controls are form-associated custom elements: they attach their value through ElementInternals, so a plain <form> submits them, they appear in form.elements, and form.reset() restores their default value. name and value mean exactly what they mean on <input>.

Standard parameters, and which components take them
ParameterBehaves asOn
name, value Submitted name/value pair; participates in form.reset() vf-button, vf-checkbox, vf-radio-group, vf-select, vf-slider, the three fields
disabled Blocks interaction and removes the control from the tab order; also honors an ancestor <fieldset disabled>. Dims the label, not the chrome — System 7 kept borders and glyphs black Every interactive component
readonly, placeholder Passed to the inner <input>/<textarea> vf-text-field, vf-text-area, vf-number-field
type Passed to the inner <input type> (text, password, email, …); on vf-button it is button/submit/reset vf-text-field, vf-button
min, max, step Clamping and stepping as on <input type="number"> / range vf-number-field, vf-slider

Naming a control

A vf-* control's focusable element lives inside its shadow root, where an aria-label on the host cannot reach it. Two routes reach it instead, and both are wired for you:

  • <vf-label for="id"> — clicking the caption focuses the target, and the caption text becomes its accessible name. It never overwrites a name you set, and puts back what it found when removed.
  • the control's own label property, for a control with no visible caption (vf-select, vf-slider, vf-list, vf-scroll-area, vf-progress-bar, vf-swatch, vf-radio-group, the three fields).

Where the role sits on the host itself (vf-radio-group, vf-list), plain aria-labelledby works too.

Roles and keyboard

Roles follow WAI-ARIA 1.2 and the keyboard behavior follows the matching APG pattern, with System 7 behavior layered on top where the two agree (classic Mac radio groups also select on arrow, which is what the APG prescribes).

Keyboard focus is drawn in the 1-bit idiom

Full keyboard access postdates System 7, so a focus affordance is something this kit adds — and it draws it in the kit's own vocabulary rather than leaving the browser's ring on top of the artwork. Where a control can carry the mark itself it does, as a 1px dashed rule on the system-pixel grid: inside the control under the ink it marks, or below the whole box where there is no interior to give. Only the controls with no face to draw on — a window's close and zoom boxes, a list row, a scroll viewport — keep a dotted ring.

Either way it is keyboard-only: a mouse click never draws it. Tab through the specimens below to see all three.

Events

Custom events are named vf-* and dispatched bubbles: true, composed: true, so one delegated listener on an ancestor sees them all however deep the shadow roots go. Native events are untouched: click, focus, keydown and friends work as they always do.

The whole event vocabulary
EventDetailFired by
vf-input { value } — { value, valueAsNumber } on the number field The three fields, vf-slider — every keystroke or drag move
vf-change { value }, { checked } (checkbox), { value, values } (list) Every value-bearing control, on commit
vf-menu-select { value, item } vf-menu-item. Deliberately not vf-select: that would collide with the popup control's own event on any delegated listener
vf-close {} on a window; { reason: 'escape' | 'close' } on a modal vf-window, vf-dialog, vf-alert

Styling: parts and tokens

Two supported surfaces, both standard CSS: every visual constant is a custom property (the token table), and each component's internals are reachable through ::part(). The per-component tables below list the parts each one exposes.

vf-desktop

The gray desktop container: the classic 50% dither drawn as a crisp SVG tile, plus window management. It stacks slotted vf-window children — a pointerdown brings a window to front and marks it active, clearing active on the others.

Utility windows (variant="utility") live on a floating tier above every document window and stand outside the single-active rule both ways, so clicking a palette never deactivates the document you are working in.

No parameters of its own. Give it a height; it is position: relative already, so position windows inside it absolutely.

vf-window

The desktop-window shell, parameterized from the full document window down to the slim windoid. The 1992 Macintosh Human Interface Guidelines names five standard windows; the kit does not ship five components — it ships two shells, and each archetype is a one-line recipe over them.

The five HIG archetypes as recipes
ArchetypeRecipe
Document window<vf-window closable zoomable movable resizable scrollbars="both">
Movable modal dialog box<vf-dialog heading="…">
Modal dialog box<vf-dialog frame="plain">
Modeless dialog box<vf-window closable movable>
Utility (floating) window<vf-window variant="utility" movable>

Parameters rather than fixed anatomies because the HIG disagrees with itself about the details — Figure 5-1 and Figure 6-1 label the same two artworks opposite ways, the close box migrating between the movable modal and the modeless dialog. The recipes follow the Chapter 6 body text, but the components stay neutral: they enable HIG compliance rather than enforcing one reading.

The modal-dialog shell, wrapping a native <dialog> for the top layer and its focus trap. Movable modal by default (striped bar, draggable, no close box); the dBoxProc modal dialog box with frame="plain". No backdrop dimming — System 7 had none.

vf-button-group

Arranges buttons in a row, sizing them all to the widest — the classic System 7 shared width — and aligning their faces. That second part is the point: a variant="default" button reserves 4px of margin for its ring, so an ad-hoc flex row lines up the ring instead of the button. Compare the two stages below.

vf-swatch

A color-swatch button: a white-inset color well sized in system pixels — a palette cell. With no color it shows the transparency checker, and a translucent value layers over that checker so partial opacity reads as partial.

The default is the flat well — 1px black border, no depth — because the swatch's usual home is a table of them, where every cell shadowing its neighbour reads as noise. shadow opts into the kit's hard drop shadow for the case that wants it: the lone well standing in for a current color, raised like the windows and menus it shares --vf-shadow-offset with.

vf-select & vf-option

The popup menu control. Two pointer styles coexist and are resolved at the first release: System 7 press-drag-release (press the pill, drag onto an item, release to pick) and modern click-to-open (a quick tap leaves the list open for a second click). Selecting blinks the row ~3 times in ~250ms, then closes.

The panel opens with the selected row laid directly over the closed pill, so the label does not move, and the control hugs the widest option — so the value never shifts as the selection changes. Give it a floor with min-width on the host if you want one.

vf-menu-bar, vf-menu & vf-menu-item

Pull-down menus with the classic press-drag-release: press a title, slide onto a command, release to run it. Sliding sideways onto another title switches menus mid-press; releasing over a disabled row, a separator or off the menu closes with nothing chosen. A quick in-place tap instead leaves the menu dropped for a second, independent click — both styles, one gesture model, disambiguated only by an in-place release.

Selecting a command blinks the row ~3 times in ~250ms (skipped under prefers-reduced-motion) and then fires vf-menu-select.

A vf-menu works standing alone too — it hosts the press gesture itself when there is no bar to own it:

vf-scroll-area

A container with System 7 scrollbars: 16px cells, a dot-dither trough, the white elevator, and hollow arrow glyphs that fill solid when pressed. Each reserved axis behaves the way System 7 did — the rail is a permanent placeholder, an empty white channel, and only fills in when the content actually overflows.

Inside a vf-window, a non-frontmost window's rails blank entirely on both axes, per the HIG. For rails on a window's own frame rather than inset in its body, use vf-window[scrollbars], which renders this composition from its own shadow tree.

vf-grid

A lattice of equal cells with 1px rules between them: the HIG's 3×3 tool palette, a color picker's swatch table, a pattern chooser. The rules are a masked lattice rather than gaps showing a black background, so the pen switches from solid to dashed with no change in layout and the color stays a token. They paint under the cells, so an item spanning two cells covers the boundary it swallowed and a cell's own ink is never crossed.

A cell is centered in its well on both axes, because what a palette holds is normally smaller than the well — a 16px icon in a 26px cell. A cell that means to fill its well instead, like a tool button that inverts black when selected, asks with place-self: stretch; under collapse that is already the default, those cells existing to meet the lines.

Semantics are yours: the grid takes no role, no keyboard behavior and no selection. Put role="group" on the host for a tool palette, role="radiogroup" for a picker, nothing at all for a plain tiling.

vf-stack

The layout primitive: a flexbox whose gap, pad, width and height are declared in whole system pixels — the art's own unit — and converted internally, so a window's insides need no calc(var(--vf-scale, 1) * …) in your stylesheet.

It exists because a page's own CSS often cannot say "8 system px". Scaling is per component: each element sets --vf-scale on itself, never on the document, so var(--vf-scale, 1) in your stylesheet resolves only where the rule's element happens to sit inside a vf-* ancestor and inherit it. For a plain <div> on an ordinary page the fallback 1 wins and the gap comes out 3× too tight, silently. A component always has the unit, because it is the scope.

Whole system px is the only expressible value, so the gap half of the layout contract holds by construction; a declared width covers the size half. It paints nothing and takes no role — what it holds decides what it is — and it is the kit's one typographically transparent component: face, line box, color and selectability all return to inherit, because wrapping content in a layout box must not change how that content reads.

The content governs the box. A column is as wide as its widest child and a row as tall as its tallest; children keep the size they were drawn at, because System 7 boxes are the size they are. The stack distributes — it never resizes. That is also why it shrink-wraps: a layout box that claimed its parent's whole width would be handing out a size nobody declared.

vf-label

The static caption: "Name:" beside a field, "Mode" over a radio group, a readout. Chrome type on a 16px line box — stated in whole system pixels, so a column of captions accumulates whole offsets with nothing for the page to remember.

for does what a native <label for> does: clicking focuses the target (a focus shortcut, not an activation — the kit's toggles carry their own labels), and the caption text becomes the target's accessible name by whichever route reaches it. It never overwrites a name you set, and puts back what it found when the label is removed or its text changes.

Design tokens

Every visual constant, with its inlined fallback. Override at :root, on a subtree, or on one element. Every length below is a system pixel value — the components do the device-pixel arithmetic themselves, so a re-themed metric stays crisp on any display.

Line boxes are lengths too. Every line-height in the kit is stated in whole system px, never as a ratio — re-theme these with whole numbers, or you put the components below them off the device-pixel grid.

Authoring a control on the kit's terms

VfToggleControl is a mixin rather than a plain base class, because the kit's two toggles sit on different bases: vf-checkbox extends VfFormControl (it submits a value under a name), while vf-radio is deliberately not form-associated — its group is the form surface. Apply it over whichever base your control needs: 

class MyToggle extends VfToggleControl(VfFormControl) {
  @property({ type: Boolean, reflect: true }) override checked = false
  protected override get toggleInternals() { return this.internals }
  protected override get toggleDisabled() { return this.isDisabled }
  protected override activate() {
    this.checked = !this.checked
    this.focus()
    emit(this, 'vf-change', { checked: this.checked })
  }
}

You get the click/Space wiring (including the held-Space auto-repeat guard), one disabled gate every activation passes through, aria-checked/aria-disabled mirroring, and a self-managed host tabindex that never clobbers a consumer's own.
