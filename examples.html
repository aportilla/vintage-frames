Vintage Frames

The component reference for a System 7 UI kit: every element, the parameters it takes, and a live specimen of each state. It opens with the components introducing themselves.

Install

npm install vintage-frames
import 'vintage-frames' // registers every <vf-*> element

That is the whole setup — the kit ships no stylesheet. Every visual constant is a --vf-* custom property with an inlined fallback, the two System 7 bitmap faces register themselves on document.fonts from inside the components, and vf-desktop paints its own gray dither — so a component dropped on a blank page renders correctly with no global CSS at all. Page-level looks (a full-bleed desktop, your own copy's face) belong to your page's stylesheet, where a component cannot and should not reach.

The root import registers all 30 elements. To ship less, import the ones you use by name — same elements, same self-registration, one module each: 

import 'vintage-frames/vf-button.js'
import 'vintage-frames/vf-checkbox.js'

Those subpaths are the whole export surface; a deeper path into the package fails at resolve time rather than as a 404 in production. It stays one npm package on purpose — the scaling, grid snapping, focus modality and font registration are module-scoped singletons, so one package is what guarantees one copy of them.

Sizing takes care of itself

Components are authored in system pixels — the 1-bit art grid — and each one maps a system pixel onto a whole number of device pixels by itself, so the artwork stays crisp at any devicePixelRatio and re-adapts when the window moves to a different display or the reader zooms the page. It is internal, it needs no setup, and nesting never compounds it.

What follows from that: a component's box is never stated in fixed CSS pixels. Windows and dialogs declare their own size in system px — <vf-window width="240" height="176"> — and for anything else a demo below sizes in em against the component's own type (on a vf-* host 1em is the kit's 16-pixel face, so 15em is the same box on every display) or as a percentage of its container. Page furniture around the components stays in ordinary px, as your own layout would.

Position is stated the same way: nearly every component takes top/left in whole system px and absolutely positions itself within its parent — it is how every window and icon on this page's desktops is placed. The details, and the few elements that don't take the pair, are under Standards & conventions.

Zoom is followed, in whole steps

Browser zoom (⌘+ / ⌘−) moves the target with the reader: the kit renders round(3 × zoom) device pixels per system pixel, so at 200% the art is 6 device px per system px — twice the size, still not one gray pixel. A response that must land on whole device pixels is a stepped one, and the steps are the same on every display:

zoomdevice px per system pxsize vs 100%
50–80%267%
90–110%3100%
125%4133%
150–175%5167%
200%6200%
300%9300%

Three details worth knowing. The steps nearest 100% hold still — 90% and 110% both round to 3, because below 3 device px per system px there is no finer move that keeps 1-bit art crisp. Ties round up — 150% renders 167% of true size, not 133%: a zoom is a request for larger, and the kit errs in the direction the reader asked. And the response is the same in every engine — Chrome and Firefox report zoom through devicePixelRatio, Safari holds its devicePixelRatio at the hardware and moves the viewport instead, and the kit tracks both signals — so a zoomed page renders the components the same size whichever browser is reading it.

Two boundaries, both deliberate. Pinch-to-zoom is not followed — it magnifies pixels that are already rasterized, at compositing time, so there is nothing the kit could re-draw for. And a page that pins --vf-scale has opted out along with the rest of the scaling: a value in scope always wins, and the pinned page then scales under zoom the way its ordinary CSS does.

One thing a host page decides

Everything else in this reference is per-component. This one is page-wide, and getting it wrong is what makes an otherwise correct integration look muddy — so it comes first: the device-pixel grid.

Staying on the device-pixel grid

A component is built entirely from whole system pixels, so every edge inside it sits on the grid — but only relative to its own origin. Land that origin, or its size, on a fractional device pixel and the whole 1-bit interior rasterizes wrong: pixel-stepped corners staircase asymmetrically, hairline borders and bitmap glyph stems smear across two device rows and go gray. Mapping a system pixel onto a whole number of device pixels is the kit's own half of that and it is handled internally, at any display density and any browser zoom. Two rules are the page's, and one call covers the first:

  1. State every line-height in whole pixels, and keep padding, margin and gap on integers — or call applyGridSnap() and forget it. Line boxes are the biggest offender: 1.65 × 17px = 28.05px, and every line of prose nudges everything after it further off.
  2. Position a box that contains components from its start edge — or give it a whole-pixel size. Anything right-aligned, centered or sharing space-between computes its origin as edge − width, so a width derived from a text run lands it off the grid. 
import { applyGridSnap, requestGridSnap } from 'vintage-frames'

applyGridSnap()    // every component measures its own paint and cancels the
                   // fractional remainder — returns a cleanup function
requestGridSnap()  // re-run after moving components in a way that resizes nothing

The correction is applied inside each component's shadow root, so the host's own position, left/top and margin are never touched and it cannot collide with your layout. Its whole footprint on your DOM is two reserved custom properties (--vf-snap-dx / --vf-snap-dy) on each corrected host. Opt a single element out with the nosnap attribute.

This page calls it. Load ?nosnap to turn it off and A/B at 100% zoom. Text you set on the kit's own faces has another option: vf-paragraph and vf-label state their line box in whole system pixels themselves.

npm run verify:grid checks every vf-* host on a page at dpr 1/2/3, and npm run verify:snap checks that a page knocked off the grid gets back on it. Point them at your own pages with VF_GRID_PAGES / VF_SNAP_PAGES.

Standards & conventions

The rest of this page documents what the kit adds. Everything a control shares with the platform behaves the way the platform says it does, and is stated once here rather than repeated per component.

Attributes and properties

Every documented property is also an attribute of the same name in lowercase (cellWidth → cell-width is the only camelCase pair). Boolean properties are boolean attributes: present means true, and the value is ignored — disabled and disabled="false" both disable. Set a boolean to false from JavaScript (el.disabled = false) or remove the attribute.

Form participation

The value-bearing controls are form-associated custom elements: they attach their value through ElementInternals, so a plain <form> submits them, they appear in form.elements, and form.reset() restores their default value. name and value mean exactly what they mean on <input> — and so does required: constraint validation is real. form.reportValidity() blocks on an empty required control with the native message, :invalid matches on the host, checkValidity/setCustomValidity/validity are all there, and Enter in a field cannot submit past a failing constraint.

Naming and describing a control

A vf-* control's focusable element often lives inside its shadow root, where a host-level attribute cannot reach it on its own. The kit bridges the gap, so every route the platform taught you works:

  • the platform's own vocabulary — <label for="id">, or aria-label/aria-labelledby on the host — resolved in html-aam precedence and handed to the inner control (vf-select, vf-swatch, the three fields);
  • <vf-label for="id"> — clicking the caption focuses the target, and the caption text becomes its accessible name. It never overwrites a name the target already has — including one computed from the target's own text, the way a vf-checkbox or a button names itself;
  • the control's own label property (vf-select, vf-slider, vf-list, vf-scroll-area, vf-progress-bar, vf-swatch, vf-radio-group, the three fields), which beats every host channel.

Where the role sits on the host itself (vf-radio-group, vf-list), plain aria-labelledby always worked — no bridge involved.

Descriptions ride the same bridge: a description property on the fields and vf-select — or aria-describedby on the host — reaches assistive tech, and while a control is invalid its validationMessage joins the same channel, so the error is announced where the hint is.

Keyboard focus is drawn in the 1-bit idiom

Full keyboard access postdates System 7, so a focus affordance is something this kit adds — and it draws it in the kit's own vocabulary rather than leaving the browser's ring on top of the artwork. Where a control can carry the mark itself it does, as a 1px dashed rule on the system-pixel grid: inside the control under the ink it marks, or below the whole box where there is no interior to give. Only the controls with no face to draw on — a window's close and zoom boxes, a list row, a scroll viewport — keep a dotted ring.

Either way it is keyboard-only: a mouse click never draws it. Tab through the specimens below to see all three.

Events

Custom events are named vf-* and dispatched bubbles: true, composed: true, so one delegated listener on an ancestor sees them all however deep the shadow roots go. Native events are untouched: click, focus, keydown and friends work as they always do.

vf-desktop

The gray desktop container: the classic 50% dither drawn as a crisp SVG tile, plus window management. It stacks slotted vf-window children — a pointerdown or keyboard focus entering a window brings it to front and marks it active, clearing active on the others. The windows' DOM order is kept in step with the stacking, so tabbing walks the stack the way the eye does — worth knowing if you style windows by :nth-child or lean on their source order.

Utility windows (variant="utility") live on a floating tier above every document window and stand outside the single-active rule both ways, so clicking a palette never deactivates the document you are working in.

Always explicitly sized: width/height in system px, never your stylesheet — the component's own inline size wins. Set the numbers directly, or let fitWithin derive them from a box you measure; then position the sized desktop with your own CSS. The windows and icons inside place themselves, with their own top/left in system px.

vf-window

The desktop-window shell, parameterized from the full document window down to the slim windoid. The 1992 Macintosh Human Interface Guidelines names five standard windows; the kit does not ship five components — it ships two shells, and each archetype is a one-line recipe over them.

vf-swatch

A color-swatch button: a white-inset color well sized in system pixels — a palette cell. With no color it shows the transparency checker, and a translucent value layers over that checker so partial opacity reads as partial.

vf-select & vf-option

The popup menu control. Two pointer styles coexist and are resolved at the first release: System 7 press-drag-release (press the pill, drag onto an item, release to pick) and modern click-to-open (a quick tap leaves the list open for a second click). Selecting blinks the row ~3 times in ~250ms, then closes.

The panel opens with the selected row laid directly over the closed pill, so the label does not move, and the control hugs the widest option — so the value never shifts as the selection changes. Give it a floor with min-width on the host if you want one.

A list taller than the screen is clipped, never scrolled — System 7 put no scrollbar on a menu. The edge slot with items beyond it shows a solid arrow instead of a row; rest the pointer on it and the list rolls through one row at a time, until the arrow runs out and disappears. Both edges can overflow at once. The clamp gives ground a whole row at a time, so even a clipped popup opens with its selected row over the closed pill.

A panel that had to slide to fit the screen opens with blank rows at whichever end the list no longer reaches — above it when the panel slid up, below it when it slid down. That looks like a mistake until you scroll: the panel keeps every slot the list asked for, and the blank is the exact travel the list rolls through, so reaching that end fills the panel precisely with no arrow left. Only a list too long for the screen band at all settles at the band's height and keeps an arrow for good. Set --vf-popup-inset-top once on :root to keep clamped panels clear of a menu bar (24px for a vf-menu-bar).

vf-grid

A lattice of equal cells with 1px rules between them: the HIG's 3×3 tool palette, a color picker's swatch table, a pattern chooser. The rules are a masked lattice rather than gaps showing a black background, so the pen switches from solid to dashed with no change in layout and the color stays a token. They paint under the cells, so an item spanning two cells covers the boundary it swallowed and a cell's own ink is never crossed.

A cell is centered in its well on both axes, because what a palette holds is normally smaller than the well — a 16px icon in a 26px cell. A cell that means to fill its well instead, like a tool button that inverts black when selected, asks with place-self: stretch; under collapse that is already the default, those cells existing to meet the lines.

Semantics are yours: the grid takes no role, no keyboard behavior and no selection. Put role="group" on the host for a tool palette, role="radiogroup" for a picker, nothing at all for a plain tiling.

vf-stack

The layout primitive: a flexbox whose gap, pad, width and height are declared in whole system pixels — the art's own unit — and converted internally, so a window's insides need no calc(var(--vf-scale, 1) * …) in your stylesheet. It is one of two stylesheet-free ways to lay those insides out — the other is placing each child with its own top/left, the DITL way (see Standards & conventions).

It exists because a page's own CSS often cannot say "8 system px". Scaling is per component: each element sets --vf-scale on itself, never on the document, so var(--vf-scale, 1) in your stylesheet resolves only where the rule's element happens to sit inside a vf-* ancestor and inherit it. For a plain <div> on an ordinary page the fallback 1 wins and the gap comes out 3× too tight, silently. A component always has the unit, because it is the scope.

Whole system px is the only expressible value, so the gap half of the layout contract holds by construction; a declared width covers the size half. It paints nothing and takes no role — what it holds decides what it is — and it is the kit's one typographically transparent component: face, line box, color and selectability all return to inherit, because wrapping content in a layout box must not change how that content reads.

The content governs the box. A column is as wide as its widest child and a row as tall as its tallest; children keep the size they were drawn at, because System 7 boxes are the size they are. The stack distributes — it never resizes. That is also why it shrink-wraps: a layout box that claimed its parent's whole width would be handing out a size nobody declared.

vf-icon

The Finder icon. vf-img puts a picture on the grid; this makes it the unit the Finder actually manipulates — a picture and a caption that select, move and rename together.

The art arrives by slot, one per icon-resource size: large is the 32×32 ICN# and small the 16×16 ics#. size picks which one paints and the cell it paints in, and the cell is reserved whether or not there is art for it — a folder is 32×20 of ink and a document 25×32, and a row of them keeps one baseline only because the cell, not the ink, is the unit.

open is the Finder's other visual state: the window an icon stands for is on screen, so the art redraws as a ghost — its outline held, its interior re-filled with the same loose dither the scroll rails use. There is no second raster and no second fetch: the ghost is derived from the slotted art itself, in the client, by canvas compositing alone. No pixels are ever read back, so a cross-origin image that taints its canvas still works — taint forbids reading, not drawing.

A name is never abbreviated, and never folded — no ellipsis, no clipping, no wrapping. System 7 solved the long-name problem at the other end — HFS capped a filename at 31 characters — so the Finder could afford to always draw the name in full, and did. Wider than its cell, a name simply overflows it, centered, the way a name wider than a 32-pixel icon always did. width is the cell — the grid pitch — not a bound on the name.

It is also what keeps the name crisp. The frame centers two things over one axis, and a centered child sits at (box − child) / 2, whole exactly when the two share a parity; half a system pixel smears a 1-bit stem across two device columns and greys it, while the plate behind it stays sharp — backgrounds are pixel-snapped by the compositor and glyphs are not. So the plate is measured from its text and sized to a whole even number of system px, which makes every offset whole by construction. One line is part of that argument: one run, one width, one parity. Your side of it is a single rule — a declared width must be even, since the component cannot round a number you chose.

Authoring a control on the kit's terms

VfToggleControl is a mixin rather than a plain base class, because the kit's two toggles sit on different bases: vf-checkbox extends VfFormControl (it submits a value under a name), while vf-radio is deliberately not form-associated — its group is the form surface. Apply it over whichever base your control needs: 

class MyToggle extends VfToggleControl(VfFormControl) {
  @property({ type: Boolean, reflect: true }) override checked = false
  protected override get toggleInternals() { return this.internals }
  protected override get toggleDisabled() { return this.isDisabled }
  protected override activate() {
    this.checked = !this.checked
    this.focus()
    emit(this, 'vf-change', { checked: this.checked })
  }
}

You get the click/Space wiring (including the held-Space auto-repeat guard), one disabled gate every activation passes through, aria-checked/aria-disabled mirroring, and a self-managed host tabindex that never clobbers a consumer's own.
