Vintage Frames

Install

npm install vintage-frames
import 'vintage-frames' // registers every <vf-*> element

The root import registers all the Vintage Frames elements. You can also import just the individual elements you need. 

import 'vintage-frames/vf-button.js'
import 'vintage-frames/vf-checkbox.js'

vf-desktop

The gray desktop container: a 50% dither, plus window management. A pointerdown or keyboard focus entering a slotted vf-window brings it to front and marks it active, clearing active on the others. DOM order is kept in step with the stacking, so tabbing walks the stack — worth knowing if you style windows by :nth-child. Utility windows float on their own tier above the document windows, outside the single-active rule both ways.

Always explicitly sized in system px, never from your stylesheet — the component's own inline size wins. Set the numbers directly or let fitWithin derive them, then position the sized desktop with your own CSS. The windows and icons inside place themselves with their own top/left.

vf-select & vf-option

The popup menu control. Two pointer styles coexist, resolved at the first release: press-drag-release (press the pill, drag onto an item, release to pick) and click-to-open (a quick tap leaves the list open for a second click). Selecting blinks the row ~3 times in ~250ms, then closes.

The panel opens with the selected row over the closed pill, so the label does not move, and the control hugs its widest option, so the value never shifts as the selection changes. Give it a floor with min-width on the host.

A list taller than the screen is clipped, not scrolled — System 7 put no scrollbar on a menu. The edge row with items beyond it shows a solid arrow instead; rest the pointer on it and the list rolls a row at a time until the arrow runs out. The clamp gives ground a whole row at a time, so a clipped panel still opens with its selected row over the closed pill, and the end it no longer reaches opens as blank rows — the travel it will roll through. Set --vf-popup-inset-top once on :root to keep clamped panels clear of a menu bar (24px for a vf-menu-bar).

vf-grid

A lattice of equal cells with 1px rules between them: a tool palette, a color picker's swatch table, a pattern chooser. Switching the pen from solid to dashed changes no layout, and the rules run behind the cells, so an item spanning two cells covers the boundary it swallowed.

A cell is centered in its well on both axes — a palette usually holds something smaller than the well, a 16px icon in a 26px cell. A cell that means to fill its well asks with place-self: stretch; under collapse that is already the default. Semantics are yours: the grid takes no role, no keyboard behavior and no selection. Put role="group" on the host for a tool palette, role="radiogroup" for a picker, nothing for a plain tiling.

vf-stack

A flexbox whose gap, pad, width and height are declared in whole system pixels — one of the two ways to lay a window's insides out without a stylesheet. The other is placing each child by coordinate, below.

A page's own stylesheet cannot state system pixels: scaling is per component — each element sets --vf-scale on itself, never on the document — so var(--vf-scale, 1) outside a vf-* ancestor falls back to 1 and comes out 3× too tight, silently.

The content governs the box. A column is as wide as its widest child and a row as tall as its tallest; children keep the size they were drawn at. The stack distributes, never resizes, and shrink-wraps. It paints nothing, takes no role, and returns face, line box, color and selectability to inherit.

Properties
NameTypeDefaultNotes
direction'column' | 'row''column'A stack is vertical unless it says otherwise
gapnumber0Whole system px between children
padstring | number—Whole system px, one to four values in CSS shorthand order (pad="12", pad="10 12", pad="14 12 10"). Leave it off inside a vf-window body, which carries its own 12px inset
place'start' | 'center' | 'end'per directionWhere the children sit across the stack. Unset resolves to start down a column and center across a row. There is no justify. Centering halves the free space, so an odd count of system px would leave a child on a half pixel — a 16px caption centered against the 25-system-px vf-number-field sits at 4.5 — and the stack steps that back onto whole system px, the exact half going toward the start. (It is place and not align because align is a legacy HTML presentation attribute browsers map to text-align on any element.)
width, heightnumber—Whole system px. Optional — a column is otherwise as wide as its widest child. Worth declaring on a panel's outermost stack: the box is then on the device-pixel grid by construction, and so is everything filled to it. In a row, a declared width is also what creates the slack a child's fill-width divides
fill-width, fill-heightbooleanfalseBare attributes on a child: be as wide (tall) as this stack allows. Each names the outcome, not an axis, so the stack compiles it to the main or cross axis depending on which way it runs. The cross axis always has a size; the main axis only has slack if you declared one — so fill-width always works in a column and needs a declared width in a row, and fill-height is the other way round. A fill with nothing to take is inert, not an error; two children filling along the main axis come out equal. A stack reads both about itself too, for parents that aren't stacks (a window body, a fieldset, a scroll well)
Slot: default. Children are flex: 0 0 auto, and a light-DOM declaration beats anything here, so align-self: stretch in your own stylesheet is the escape hatch for a cross-axis fill a direction doesn't offer. No parts, tokens, events or role. Not a vf-button-group (which equalizes widths and aligns faces) and not a grid.

The other way: top and left

Every component takes top and left in whole system px — no exceptions. Set either and the element is absolutely positioned within its parent, the coordinate you left out defaulting to 0; set neither and it renders in flow. (0,0) is CSS's nearest positioned ancestor, and every kit container is one — a container of your own needs position: relative, or is a vf-container, below.

That includes the rows a container usually owns — vf-option, vf-menu-item, vf-list-item and a bar's vf-menu. Where you put one is your call. Just know what the parent stops doing once a child leaves its flow: a select or menu panel is as wide as its widest flowed row and no longer counts a placed one, the popup's scroll clamp skips it too, and the rows after it close the gap. That's the placement working — but it isn't how a popup, pulldown or list box is laid out, so reach for it when the row really is standing alone.

vf-dialog takes the pair in viewport coordinates: showModal() puts a modal in the top layer, whose containing block is the viewport, so that one origin is the screen's rather than the parent's — same unit and same behavior otherwise, with unset meaning centered. A drag writes through the same two properties, so read a moved element's position off el.left rather than style.left, which holds a live calc().

vf-container

A box that is nothing but its declared size — width and height in whole system px around anything you slot into it. It paints nothing and has no layout opinion: in-flow children get normal flow, placed children get a coordinate system. It exists because placing children with top/left needs a positioned ancestor, and a region of your own otherwise needs position: relative in a stylesheet — this is that region as an element.

It is not a vf-stack: the stack is a flexbox with opinions — an axis, a cross-axis default, fills compiled into flex. Reach for the container when those opinions are the thing in the way — a field of placed icons, a fixed stage for placed art, a composition that brings its own layout with it.

Properties

Slot: default. Takes top/left like nearly every component, so a container is itself placeable — inside a window, a desktop, another container. The static caption: "Name:" beside a field, "Mode" over a radio group, a readout. Chrome type on a 16px line box, stated in whole system pixels, so a column of captions accumulates whole offsets.

The Finder icon. vf-img puts a picture on the grid; this makes it a control — a picture and a caption that select, move and rename together.

Sizing and the device-pixel grid

Components are authored in system pixels — the 1-bit art grid, where a border is 1 and a push button 20 tall. On a Macintosh that pixel was 1/72 inch, and reproducing it is the whole job: each component asks the display how dense it is and renders one system pixel as the whole number of device pixels nearest that size, round(96/72 × devicePixelRatio) — 96 being CSS's reference dpi, the only density anchor a browser exposes.

The count is always whole because the art has to land on the device-pixel grid — that is the one thing that never bends. Where rounding to a whole count is not enough, the count steps again: a 3× display would like 4 device pixels, but 4/3 is not a length a browser's layout grid can hold, so its dithers would drift off-grid a fraction further with every repeat. It takes 3 instead. Size yields to the grid, never the other way round.

So the same button is 20 CSS px tall on a 1× monitor and 30 on a 2× one, landing within a quarter of its 1984 physical size on both. Pin it instead by declaring --vf-scale in a stylesheet the page loads before the components upgrade — :root { --vf-scale: 1 } is a fixed 20-px button everywhere — and keep --vf-scale × devicePixelRatio whole when you do. This page pins nothing, so every specimen above is self-scaled.

A component's box is therefore never stated in fixed CSS pixels. Windows, dialogs and the other declared boxes take their size in system px (<vf-window width="240" height="176">); the demos above size everything else in em against the component's own type (on a vf-* host 1em is the kit's 16-pixel face) or as a percentage of its container.

Zoom

Zoom needs no rule of its own. Zooming multiplies device pixels per CSS pixel — that is what zoom is — so it arrives as a denser display and walks the same table: a 2× display at 200% zoom is density 4, which wants 5 device pixels per system pixel. The art grows with the page instead of dividing the zoom back out.

  • The target is a step function, so zoom sometimes changes nothing — 100% and 125% on a 2× display both round to 3 device pixels, and the art holds still while the copy around it grows. That is the nearest whole count being the same count, not a bug; bending it to feel responsive would put the art off the grid.
  • Chrome and Firefox report zoom through devicePixelRatio; Safari holds it at the hardware and moves the viewport instead. The kit tracks both.
  • Pinch-to-zoom is not followed — it magnifies already-rasterized pixels at compositing time. A pinned --vf-scale opts out of density-following as well.

Staying on the grid

A component is built from whole system pixels, so every edge inside it sits on the grid — but only relative to its own origin. Land that origin, or its size, on a fractional device pixel and the 1-bit interior rasterizes wrong: stepped corners staircase asymmetrically, hairline borders and glyph stems smear across two device rows and go gray. Two rules are the page's, and one call covers the first:

  1. State every line-height in whole pixels, and keep padding, margin and gap on integers — or call applyGridSnap() and forget it. Line boxes are the biggest offender: 1.65 × 17px = 28.05px, and every line of prose nudges everything after it further off.
  2. Position a box that contains components from its start edge — or give it a whole-pixel size. Anything right-aligned, centered or sharing space-between computes its origin as edge − width, so a width derived from a text run lands it off the grid. 
import { applyGridSnap, requestGridSnap } from 'vintage-frames'

applyGridSnap()    // every component measures its own paint and cancels the
                   // fractional remainder — returns a cleanup function
requestGridSnap()  // re-run after moving components in a way that resizes nothing

The correction never touches the host's own position, left/top or margin; its whole footprint on your DOM is --vf-snap-dx / --vf-snap-dy on each corrected host. Opt one element out with nosnap. This page calls it — load ?nosnap to compare with it off at 100% zoom. vf-paragraph and vf-label state their line box in whole system pixels, so text set on them satisfies rule 1 without the call.

npm run verify:grid checks every vf-* host at dpr 1/2/3, and npm run verify:snap checks that a page knocked off the grid gets back on it. Point them at your own pages with VF_GRID_PAGES / VF_SNAP_PAGES.

Focus

Keyboard focus is added rather than reproduced — keyboard access postdates System 7 — so the kit draws its own mark instead of leaving the browser's ring: a 1px dashed rule on the system-pixel grid, inside the control under the ink it marks (a button's label, a checkbox's box, a field's well), or below the whole box where there is no interior to give (a popup menu, clear of its shadow; a slider, under the full rail, so the mark stays put as the handle travels). The few with no face to draw on — a window's close box, a list row, a scroll viewport — keep a dotted ring, and vf-menu and vf-select mark only while closed.

Either way it is keyboard-only: a mouse click never draws it, including on the controls where :focus-visible is true after a pointer. What the mark follows is the page's last input modality.
